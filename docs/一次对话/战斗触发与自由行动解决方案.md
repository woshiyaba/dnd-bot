# 战斗触发与自由行动解决方案

> 分析对象：`docs/一次对话/对话bug分析.md` 中 2026-07-23 的试玩对话与日志。  
> 目标：让玩家可以跳过推荐调查路线、主动制造冲突；由真实 LLM DM 确认局势是否进入战斗，再由战斗引擎接管全部规则结算。

## 一、结论

这次没有开战，不是玩家表达得不够明确，也不是 DM 不愿意开战。

玩家先说“发起进攻看看”，随后又明确说“开战”。真实 LLM DM 实际上连续三次给出了 `intent=start_combat`。战斗被拦下，是因为会话中的三份事实已经分裂：

| 层 | 当时认为的事实 |
|---|---|
| 玩家看到的叙述 | 玩家已登上钟楼之巅，古钟之灵就在面前 |
| 故事状态 | 仍在 `ruined_village` 拍、`bell_tower_hall` 场景 |
| 战斗输入 | 当前 `scene.actors` 只有神父艾达，没有 `bell_spirit` |

`src/dm/world_bridge.py` 只允许从当前 `scene.actors` 中选择 `disposition=hostile` 的 actor。于是 DM 虽然正确选择了 `bell_spirit`，校验层仍把它当作非法目标，并要求 LLM 重评成 `reply`。

因此不应简单删除 `actor_id` 校验。没有 actor 和卡面时，`src/session/graph.py::_build_combat_input` 无法构造怪物；盲目放行可能启动一场只有玩家、没有敌人的空战斗。

正确方案是：

1. 放宽故事路径，不把推荐调查内容当成进入 Boss 战的硬门槛。
2. 让 DM 对玩家行动作真实裁定，并产出结构化的“行动被接受、目标是谁、是否需要跨场景”。
3. 由会话引擎先原子化地提交场景迁移和敌对关系，再严格解析遭遇。
4. 遭遇解析成功后立刻进入战斗图，命中、伤害、HP、胜负全部由战斗引擎处理。

一句话概括：**自由应放在 DM 的世界裁定层，严格应留在引擎的规则结算层。**

## 二、这次对话暴露出的具体问题

### P0：叙述状态与真实状态分裂

玩家说“我需要直接上钟楼看看”后，DM 要求敏捷豁免，玩家以 `17 vs DC 13` 成功。

但检定成功后：

- `story.current_beat_id` 仍是 `ruined_village`；
- `story.current_location_id` 和 `scene.location` 仍是钟楼前厅；
- `scene.actors` 仍只有神父艾达；
- 最终叙述却宣布玩家已经站在钟楼顶，并让古钟之灵现身。

这说明当前系统允许叙述描述一个没有被引擎提交的世界变化。下一回合 DM 根据最近对话认为玩家在楼顶，而校验器根据 `scene` 认为玩家仍在楼下，冲突必然发生。

根因之一是 `player_check` 只有检定规格，没有“成功后应提交什么世界变化”。当前 `world_writes` 又会在检定成败之外统一消费，不能安全表达：

```json
{
  "on_success": {
    "transition_to": "bell_tower_summit"
  }
}
```

### P0：明确的战斗意图被数据错误吞掉

日志已经证明 DM 正确识别了战斗：

- “发起进攻看看”后，DM 输出 `start_combat + bell_spirit`；
- “开战”后，DM 又连续两次输出 `start_combat + bell_spirit`。

但 `_normalize_decision` 发现当前场景没有合法敌意 actor 后，将裁定退回 LLM。纠错提示又明确要求“没有合法敌人就改为 reply”，于是一个数据一致性错误被伪装成了 DM 的剧情决定。

这会产生两个体验问题：

1. 玩家必须重复表达同一行动，系统仍不执行；
2. 系统没有暴露真实错误，反而生成看似合理但事实错误的叙述。

对于已经由 DM 确认的明确战斗意图，载荷修正失败时不应悄悄降级成 `reply`。应修复遭遇引用；仍无法解析则显式失败，不能编一段“其实还没打”的内容继续剧情。

### P0：DM 越过了战斗引擎的规则边界

“开战”后的玩家可见叙述写道：

> 你的剑刃撕开褴褛的布料，在月光下溅起一串火星……

此时战斗图根本没有启动，没有先攻、攻击骰、命中判定或伤害结算。这段话却已经宣布玩家的剑击中了目标。

这违反了项目的核心原则：

> 规则归引擎，叙述归 DM，骰子归玩家。

玩家宣布攻击只代表“尝试攻击”。DM 可以确认敌人有反应、双方进入敌对状态，但第一刀是否命中必须等战斗引擎结算。

### P0：线索被错误地设计成“空气墙”

`ruined_village` 当前只有一个离开条件：三个线索 flag 全部为真，才允许进入 `bell_tower_summit`。

这把：

- 熔痕；
- 真名；
- 圣水；

从“帮助玩家削弱 Boss 的准备信息”变成了“未集齐就不能登楼”的三把钥匙。但世界描述中楼梯明明就在眼前，也没有锁死、坍塌或结界等合理阻挡。

D&D 中，玩家应当可以准备充分后挑战，也可以莽撞地直接挑战。后者的代价应是战斗更难，而不是世界拒绝承认玩家已经走上楼梯。

### P1：`clues_delivered` 与推进 flag 没有闭环

当前系统把两种状态分开记录：

- `clues_delivered`：DM 是否已经把线索讲给玩家；
- `flags`：世界事实是否成立。

但本 canon 的 `t_all_clues` 检查的是：

```json
{
  "all": [
    "clue_bell_crack",
    "clue_spirit_name",
    "clue_holy_water"
  ]
}
```

对话中 DM 多次写了 `clues_delivered`，却没有对应写入上述 flag。即使玩家已经听到“赫尔薇”，推进条件仍可能永远为假。

“已经听说”“已经亲自发现”“已经取得物品”应明确区分，不能用相同名字暗示它们会自动同步。

### P1：DM 不知道合法结构化值，却因猜错受到惩罚

日志中出现了两个被忽略的 flag：

- `quest_accepted_rusty_bell`
- `bell_tower_combat_triggered`

canon 实际白名单是 `accepted_quest`、`clue_*`、`boss_dead`，但当前拍画像没有把合法 flag、地点、遭遇 id 完整提供给 DM。LLM 只能猜名字，然后引擎静默忽略。

结构化输出需要把候选值明确给模型，不能一边隐藏枚举，一边要求模型精确命名。

### P2：行动选项变成了重复确认

玩家已经说“发起进攻看看”，DM 回复却再次建议：

> 你可以抢先出手朝它发动攻击——如果你准备好开战了……

这没有承接行动，而是把玩家已经做出的决定重新塞回选项列表。当前提示词要求每次结尾都必须给 2～3 个“你可以”选项，容易把自由对话做成菜单，也会诱发这种重复确认。

明确行动不应再次询问。选项只应在玩家迷茫、普通叙事回合结束或确实存在需要选择的分支时提供，并明确它们只是建议，不是行动白名单。

### P2：非法决策重试增加了延迟，但没有修复事实

第一次攻击从 DM 调用到最终回复约 44 秒；第二次“开战”也经历了多轮 LLM 调用。重试的目标是让 LLM 放弃正确的战斗意图，而不是补齐世界状态，因此延迟和成本都增加了，结果反而更错。

## 三、应采用的裁定原则

### 1. 玩家描述意图，DM 确认世界后果，引擎结算规则

三者职责应明确分开：

| 阶段 | 负责者 | 负责内容 |
|---|---|---|
| 行动声明 | 玩家 | “我要登楼”“我要攻击古钟之灵” |
| 世界裁定 | 真实 LLM DM | 目标是否存在、是否能接触、行动是否让双方进入战斗、是否有人措手不及 |
| 规则结算 | 引擎 | 场景提交、参战者卡面、先攻、命中、伤害、HP、胜负 |
| 结果叙述 | 真实 LLM DM | 只叙述引擎已经提交和结算的事实 |

不能用关键词或离线启发式代替 DM 的世界裁定。DM 调用失败或结构无法解析时应显式失败。

### 2. 明确攻击就是开战请求，不需要无限确认

当目标真实存在、可接触且有战斗资料时：

- “我攻击它”“我拔剑砍过去”“开战”均足以让 DM 确认进入战斗；
- 不需要 DM 再问一次“你确定吗”；
- 玩家第一刀不是自动命中，而是转化为战斗中的行动和可能的突袭条件。

只有以下情况不进入回合制战斗：

- 目标实际不在场或无法接触；
- 玩家攻击的是门、绳索等环境对象，应走世界检定或直接叙述；
- 目标被 canon 明确标记为非战斗对象，并有预写的逃跑、投降等解决方式；
- DM 根据局面裁定玩家只是威吓或试探，并未实际动手。

### 3. `disposition` 不应等同于“可否被攻击”

当前校验只有 `disposition=hostile` 才能成为战斗目标，这会阻止玩家攻击中立或友善 NPC。

更合理的定义是：

- `disposition` 表示行动前的态度；
- “能否进战斗”取决于 actor 是否在场/可达、是否有合法战斗卡面；
- 玩家主动攻击友善或中立 actor 后，由 DM 确认敌对关系变化，引擎把其放到敌对阵营。

为了避免运行时编造数值，canon 中可能遭受攻击的实体应明确提供：

- `card` 或 `combat_profile_ref`；或
- 明确的 `noncombatant_resolution`，例如逃跑、投降、不会进入回合制战斗。

不得在运行时用假 DM、临时模板或启发式数值补一张怪物卡。

### 4. 线索决定优势，不决定玩家是否有资格行动

只有世界内真实存在的障碍才应成为硬门槛，例如门确实锁着、桥确实断了、仪式确实需要钥匙。

本故事中的三条线索更适合作为预定义的战斗准备：

| 线索 | 推荐用途 |
|---|---|
| 熔痕 | 解锁针对钟体裂缝的环境/即兴行动 |
| 真名“赫尔薇” | 解锁一次预定义的动摇效果或特殊行动 |
| 圣水 | 作为真实物品进入背包，在战斗中按预定义规则使用 |

玩家一条都没拿到也可以挑战 Boss，只是没有这些优势。具体加值、状态和效果必须写进 canon/规则配置并由引擎执行，不能让 LLM 临时计算。

## 四、推荐的新流程

```text
玩家输入
   │
   ▼
DM adjudicate（真实 LLM）
确认：行动是否成立、目标是谁、是否进入战斗、是否需要场景迁移
   │
   ├─ 普通行动 ─► 引擎提交立即效果/等待玩家检定 ─► DM 叙述已提交结果
   │
   └─ start_combat
          │
          ▼
resolve_engagement（会话引擎）
校验可达性 → 提交跨拍/跨地点迁移 → 装载 actor → 提交敌对关系
          │
          ▼
resolve_encounter（会话引擎）
按 encounter_id/actor_id 从 canon 和已提交 scene 取卡面、战利品、随机种子
          │
          ▼
CombatGraph
先攻 → 行动声明 → 攻击/伤害/HP → 胜负
          │
          ▼
故事推进 + DM 叙述已结算事实
```

核心要求是：**迁移、敌人装载和进入战斗必须是同一个会话回合内的原子流程。**

这样即使玩家一句话说“我冲上钟楼直接砍那个怪物”，系统也可以先提交“抵达钟楼之巅”，再解析 `boss_bell_spirit`，随后进入战斗，而不要求玩家分两回合重复表达。

## 五、结构化决策建议

### 1. 不让 LLM 为预置 Boss 手写 `monster_ids`

canon 已有：

```json
{
  "id": "boss_bell_spirit",
  "monster_ids": ["bell_spirit"]
}
```

对于预置遭遇，DM 更适合从引擎提供的候选列表中选择 `encounter_id`：

```json
{
  "intent": "start_combat",
  "combat": {
    "source": "canon_encounter",
    "encounter_id": "boss_bell_spirit",
    "target_actor_ids": ["bell_spirit"],
    "reason": "玩家明确登上钟楼并向古钟之灵发动攻击",
    "surprised_actor_ids": ["bell_spirit"]
  },
  "before_combat": {
    "transition_to_beat_id": "bell_tower_summit",
    "move_to_location_id": "bell_tower_summit"
  }
}
```

其中：

- DM 只可从输入上下文给出的候选 `encounter_id`、actor id、beat id、location id 中选择；
- 引擎验证目标拍是否从当前拍可达；
- `monster_ids`、卡面、战利品、随机种子由引擎从 canon 展开；
- `surprised_actor_ids` 是 DM 的局势裁定，引擎只对合法参战者应用状态。

对于当前场景内临时爆发的冲突，可以使用：

```json
{
  "intent": "start_combat",
  "combat": {
    "source": "scene_actors",
    "target_actor_ids": ["some_actor"],
    "reason": "玩家主动攻击在场 NPC"
  }
}
```

### 2. 玩家检定需要条件化世界效果

`player_check` 应能携带经引擎验证的成功/失败效果：

```json
{
  "intent": "player_check",
  "check": {
    "actor_id": "pc_aldous",
    "ability": "dexterity",
    "dc": 13,
    "kind": "saving_throw",
    "prompt": "在破碎石阶上稳住身体"
  },
  "effects": {
    "on_success": {
      "transition_to_beat_id": "bell_tower_summit",
      "move_to_location_id": "bell_tower_summit"
    },
    "on_failure": {
      "stay_in_current_scene": true
    }
  }
}
```

`resolve_check` 算出成败后，新的 `apply_action_effects` 节点只提交对应分支。最终叙述只能读取已经提交的事件，不能自行宣布移动成功。

### 3. 给 DM 明确的候选值

DM 决策上下文至少应增加：

- `allowed_flags`
- `allowed_clue_ids`
- `current_beat_locations`
- `reachable_transitions`
- `current_scene_combatants`
- `reachable_encounters`

模型无需猜 `quest_accepted_rusty_bell` 之类的名字。白名单外写入不应仅静默忽略；开发日志和测试环境应将其作为结构错误暴露。

### 4. 锁定已经确认的语义意图

若第一次合法 JSON 已经是 `start_combat`，后续重试只能修正：

- encounter 引用；
- actor 引用；
- transition 引用；
- 字段格式。

不应因为载荷错误允许重试把 `start_combat` 改成 `reply`。如果引擎无法从 canon 和场景解析 DM 已确认的目标，应抛出明确错误，指出缺失的 encounter/actor/card。

## 六、本故事的 canon 调整

### 1. 把“登楼”设为正常出口

`ruined_village` 应有一个由玩家行动触发的出口，例如：

```json
{
  "id": "t_ascend_tower",
  "kind": "semantic",
  "predicate": {
    "prompt": "玩家是否已经明确尝试并成功登上钟楼之巅？"
  },
  "description": "玩家决定并成功登上钟楼之巅"
}
```

并指向：

```json
{
  "trigger_id": "t_ascend_tower",
  "next_beat_id": "bell_tower_summit"
}
```

如果登楼需要检定，不能只靠事后语义问句判断，必须由前述 `on_success` 效果提交迁移，避免失败也被误判为已到达。

### 2. 取消 `t_all_clues` 对登楼的硬阻塞

三个线索可以保留为探索目标，但不再是唯一出口条件。可以：

- 删除 `t_all_clues` 出口；或
- 将其改成“队伍已充分准备”的状态，只影响 Boss 遭遇配置，不控制能否登楼。

### 3. 明确“得知、发现、持有”的不同状态

建议拆成：

- `delivered_clues`：玩家听过相关信息，只影响 DM 避免重复讲述；
- `flags.clue_bell_crack_discovered`：玩家亲自发现熔痕；
- `flags.spirit_true_name_known`：队伍确认真名；
- 背包物品 `holy_water`：队伍确实取得圣水。

战斗准备效果读取世界事实和物品，不读取“DM 是否说过这句话”。

## 七、代码改动落点

### `src/dm/world_bridge.py`

- 把合法 flag、地点、可达拍、当前 actor、可达 encounter 候选喂给 DM。
- `start_combat` 优先返回 `encounter_id + target_actor_ids`，不让 LLM 重复 canon 里的怪物清单。
- 校验“候选引用是否合法”，不再只检查当前 `scene` 的 hostile actor。
- 已确认的 `start_combat` 载荷错误不得重评成 `reply`。
- 明确攻击时禁止生成“要不要再攻击一次”的回应计划。

### `src/session/dm_subgraph.py`

- 为 `player_check` 保存 `effects.on_success/on_failure`。
- 为 `start_combat` 保存 `before_combat` 和结构化 combat 请求。
- 检定结算后进入 `apply_action_effects`，再进行故事推进或战斗路由。

### `src/session/graph.py`

- 在 `run_combat` 前增加 `resolve_engagement`：
  1. 验证并提交跨拍/跨地点迁移；
  2. 从 canon 装载目标 actor；
  3. 必要时提交 disposition/faction 变化；
  4. 按 encounter id 展开完整战斗输入；
  5. 没有敌人卡面时显式失败，绝不启动空战斗。
- `_build_combat_input` 不再把“找不到 actor/card”静默 `continue`，应抛出带 actor id 的错误。

### `src/session/story_nodes.py`

- 最终叙述只使用已提交的 `story_transition`、`scene` 和 `campaign_log` 事件。
- 跨拍移动使用明确的 transition 请求，不再借 `moved_to` 越权，也不应静默忽略非法移动。
- 明确 `clues_delivered` 与世界 flag/物品的关系。

### `src/model/canon.py`

- 增加按 `encounter_id` 查找遭遇的能力。
- 校验 encounter 的每个 `monster_id` 能解析到带卡面的 actor/cast 条目。
- 可增加预定义 `preparation_effects`，由引擎读取线索和物品后应用。
- 若要支持玩家攻击友善/中立 NPC，校验其具备 `card/combat_profile_ref` 或显式非战斗处理策略。

### `canon/whispers_bell_tower.json`

- 增加“成功登楼”出口。
- 三线索从硬门槛改为可选准备。
- 保留 `bell_tower_summit` 的 `bell_spirit` actor 与 `boss_bell_spirit` encounter，作为引擎唯一战斗数据源。

### `src/dm/prompt.py`

## 九、回归测试与验收标准

至少增加以下自动化用例：

1. **跳过线索登楼**：玩家未取得任何线索，成功登楼后 `story.current_beat_id`、`scene.beat_id`、`scene.location_id` 均为 `bell_tower_summit`。
2. **明确攻击立即开战**：输入“发起进攻看看”后，下一状态是战斗的首个中断，而不是普通 DM 回复。
3. **复合行动**：输入“我冲上钟楼直接砍那个怪物”，同一回合完成迁移和开战。
4. **无提前命中**：首个攻击骰结算前，消息和事件流中不得出现已经命中、造成伤害或目标受伤的既定事实。
5. **遭遇完整性**：`boss_bell_spirit` 必须解析出 `bell_spirit` 卡面；缺卡时测试应明确失败。
6. **不能空战斗**：任何 `start_combat` 都必须至少有一名玩家和一名合法对立方。
7. **不降级意图**：DM 首次确认 `start_combat` 后，错误载荷不得被重评成 `reply`。
8. **可选线索**：零线索可以开战；获得线索后只改变 canon 预定义的战斗选项/效果。
9. **攻击非敌意 actor**：具备战斗资料的中立/友善在场者可在 DM 确认后转入战斗；无战斗资料时走显式预设处理，不临时造数值。
10. **结构化值可见**：DM 只使用引擎提供的 flag、location、beat、actor、encounter id，不再出现白名单外 flag 警告。

针对这次日志的直接验收结果应是：

- 不再出现 `start_combat 未给出合法敌意 actor_id`；
- 不再出现 `bell_tower_combat_triggered` 被白名单忽略；
- 玩家不需要连续说两次“打”和“开战”；
- 战斗发生前不会叙述剑刃已经命中；
- 跳过调查会让战斗更危险，但不会让世界拒绝玩家登楼。

## 十、最终原则

canon 应保证故事有结构和后果，但不应替玩家选择路线。

对这个项目，更合适的四条边界是：

> **结构归引擎，但结构不是空气墙。**  
> **世界行动归 DM 裁定，但明确行动不反复确认。**  
> **战斗数据归 canon 和场景，不能由 LLM 临时编造。**  
> **命中、伤害、HP 与胜负归战斗引擎。**
