# 故事分片并发生成方案

> 文档状态：计划实施
> 设计基线：2026-08-03
> 单一问题：所有 Canon 分片严格串行生成，单故事耗时是各分片耗时之和
> 目标文件：`src/story/generator.py`、`src/services/story_service.py`

## 1. 问题定义

当前分片顺序为：

```text
top_level -> cast -> locations -> act:* -> actions -> endings
```

3 个 Act 时共有 8 个分片。即使所有分片一次成功，也需要 8 次串行模型等待。本文只解决单个故事内部的分片并发，不讨论多个故事任务 worker。

## 2. 真实依赖关系

### 2.1 硬依赖

- 所有分片依赖已经通过校验的 StoryPlan。
- Act 和 Ending 的运行时校验可能从 Cast 取得固定 CombatCard，因此必须在 Cast 验证后落库。
- 完整 Canon 校验依赖所有分片。
- 连贯性复核依赖完整 Canon。

### 2.2 非硬依赖

- Locations 校验只依赖 Plan registry，不依赖 Cast。
- Actions 校验只依赖 Plan registry 和 owner ledger。
- top level 不依赖其它分片。
- 当前 adjacent Act 摘要只包含 Beat ID、Act ID、objective 和 exits，这些都可以从 StoryPlan 生成，不需要等待上一 Act 的创作结果。

## 3. 两波并发模型

```text
StoryPlan
  -> Wave A（限并发）
       top_level
       cast
       locations
       actions
  -> 等待 Cast 和 Wave A 完成
  -> Wave B（限并发）
       act:1 ... act:n
       endings
  -> 汇总 Canon
  -> 完整校验和连贯性复核
```

第一版使用两波结构，逻辑简单、恢复边界明确。后续如果指标证明 Wave A 的慢分片影响明显，可以只等待 Cast，其他 Wave A 任务与 Wave B 重叠运行，但不作为首版目标。

## 4. 并发控制

建议新增进程级故事模型信号量：

```python
STORY_FRAGMENT_CONCURRENCY = 3
story_fragment_semaphore = asyncio.Semaphore(STORY_FRAGMENT_CONCURRENCY)
```

默认值建议为 2，确认供应商配额后再提高到 3。不能直接对所有分片无上限 `asyncio.gather()`。

每个分片任务包含完整生命周期：

```text
begin_stage
  -> 获取 semaphore
  -> 生成/修复
  -> 最终校验
  -> persist validated artifact
  -> 释放 semaphore
```

## 5. 任务组织

优先使用 `asyncio.TaskGroup`：

- 一个分片失败时取消尚未完成的兄弟任务；
- 等待取消完成后再向上抛错；
- 已经通过校验并持久化的分片保留，任务重试时可恢复；
- 被取消或只完成模型调用但未验证的结果不得标记为 artifact。

需要为取消定义明确边界：

- 用户取消后，不再启动新的分片调用；
- 已经在供应商侧执行的请求尽力取消；
- 请求返回后先检查取消标记，再执行持久化；
- TaskGroup 退出后统一把任务标记为 cancelled 或 failed。

## 6. adjacent 上下文

将 `_adjacent_fragment_summaries()` 改为只依赖 StoryPlan：

```python
def adjacent_plan_summaries(fragment_kind: str, plan: StoryPlan) -> list[dict[str, Any]]:
    ...
```

摘要包含：

- 相邻 Act 的 purpose 和 turning point；
- Beat ID、objective、pressure；
- 入口和出口目标；
- 分支汇流点和需要回应的 payoff flags。

不传相邻 Act 的完整创作文案，避免引入串行依赖和上下文膨胀。跨 Act 文案一致性由最终连贯性复核负责。

## 7. 持久化与进度

- `artifact_key` 仍保持 `fragment:{kind}`，兼容现有恢复逻辑。
- SQLite Store 已有进程内锁，但回调中的任务进度不能依赖完成顺序。
- 进度应根据“已验证分片数 / 计划分片总数”计算。
- UI stage 应显示“并行编译 Canon（3/8）”，而不是显示最后完成的随机分片名称。
- `repair_count` 由每个分片返回独立值，汇总时相加，避免共享变量的竞态语义。

建议分片任务返回：

```python
@dataclass(slots=True)
class FragmentResult:
    fragment_kind: str
    payload: dict[str, Any]
    repair_count: int
    elapsed_ms: int
```

## 8. 限流与失败

- 供应商 429 不应立即让其它已运行分片全部重试。
- 信号量限制并发，传输层按 `Retry-After` 执行一次有限退避。
- 如果多个分片连续出现 429，当前任务停止启动新分片并显式报告容量不足。
- 不因一个分片失败而重新生成已经验证的其它分片。

## 9. 测试要求

1. Wave A 的四个分片能够重叠执行。
2. Act 校验不会在 Cast 验证前运行。
3. Wave B Act 之间不存在对已编译相邻 Act 的读取。
4. 并发数永远不超过配置值。
5. 一个分片失败时，未完成兄弟任务被取消并等待退出。
6. 已验证并持久化分片在恢复后不会重新调用模型。
7. 并发完成顺序不会造成进度回退。
8. 用户取消后不会再启动新的分片。

## 10. 验收标准

- 3 Act 故事的无修复路径从 8 段串行等待降低为 2 波等待。
- 默认并发不会超过供应商配额配置。
- 并发不改变最终 Canon 的分片覆盖、ID 和完整校验要求。
- 任一失败路径都不会留下被标记为有效的半成品。
