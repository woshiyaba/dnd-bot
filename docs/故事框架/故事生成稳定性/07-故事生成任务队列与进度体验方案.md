# 故事生成任务队列与进度体验方案

> 文档状态：计划实施
> 设计基线：2026-08-03
> 单一问题：单 worker 造成多用户排队，任务响应又缺少可解释的队列和分片级进度
> 目标文件：`src/services/story_service.py`、`src/story/store.py`、`src/schemas/story.py`、`src/api/stories.py`、`front/pc-dnd-bot/`

## 1. 问题定义

当前生成服务只有一个 `_worker_loop()`。多个用户提交后，后续任务必须等待前一个故事完全结束。任务响应只有阶段和百分比，用户无法区分：

- 正在队列等待；
- 模型仍在正常生成；
- 正在修复某个局部问题；
- 请求已经卡住；
- 取消请求何时会生效。

本文只解决任务生命周期和用户感知，不定义单故事内部的分片并发算法。

## 2. API 统一使用异步任务

PC 工作台已经使用 `POST /generation-tasks`，应把它确定为唯一推荐入口：

```text
POST   /api/stories/generation-tasks
GET    /api/stories/generation-tasks/{task_id}
DELETE /api/stories/generation-tasks/{task_id}
```

旧 `POST /drafts` 保留兼容，但：

- 不再用于官方前端；
- 文档标记为兼容接口；
- 在现有 201 同步响应契约下不承诺断线恢复，调用方需要自行承担代理超时风险；
- 新接入方必须使用任务接口；
- 后续主版本将该接口迁移为返回 202 和任务资源位置，或直接移除同步兼容入口。

## 3. 公开任务状态

建议响应增加不泄露剧情的字段：

```python
class StoryGenerationTaskResponse(BaseModel):
    task_id: str
    status: Literal[
        "queued", "running", "repairing", "completed",
        "failed", "cancel_requested", "cancelled"
    ]
    stage_code: str
    stage: str
    progress: int
    queue_position: int | None
    completed_units: int
    total_units: int
    active_units: int
    retrying: bool
    created_at: datetime
    updated_at: datetime
    error_code: str | None
    error: str | None
    draft: StoryDraftResponse | None
```

不公开 Plan、Beat ID、NPC、线索、Prompt、模型名或供应商异常。

## 4. 进度计算

百分比不能继续依赖“每完成一个分片加 5”。应按动态工作单元计算：

| 阶段 | 建议权重 |
| --- | ---: |
| 排队 | 0 |
| StoryPlan | 20 |
| 分片编译 | 55 |
| 汇总校验 | 10 |
| 连贯性复核/修复 | 15 |

分片阶段：

```text
fragment_progress = 20 + 55 * validated_fragments / total_fragments
```

修复不会让百分比倒退。处于修复状态时通过 `retrying=true` 和阶段文案说明，不虚构额外完成度。

## 5. 队列位置

Store 增加只读查询：

```python
def queue_position(task_id: str) -> int | None:
    """按 created_at 返回当前任务前方 queued 数量；running 返回 0。"""
```

队列位置是快照，不承诺精确完成时间。前端显示：

```text
等待生成，前方还有 2 个任务
```

只有积累足够真实指标后，才显示宽区间预计等待时间；不使用固定的虚假倒计时。

## 6. 多 worker 演进

先完成单故事并发上限和全局供应商信号量，再把 worker 数做成配置：

```text
STORY_TASK_WORKERS=1
STORY_GLOBAL_LLM_CONCURRENCY=3
```

关系必须满足：

```text
所有任务的总模型并发 <= STORY_GLOBAL_LLM_CONCURRENCY
```

提高到 2 个 worker 前必须确认：

- `next_queued_task()` 的领取事务不会让两个 worker 获得同一任务；
- campaign ID 预留仍保持原子；
- SQLite 写锁不会造成长事务；
- 同一 task 不会同时恢复两次；
- 供应商限流和成本允许。

第一阶段即使保持单 worker，公开 queue position 也能明显改善用户感知；多 worker 不应和 JSON 修复重构绑在同一次发布。

## 7. 取消体验

固定取消状态机：

```text
queued -> cancelled
running -> cancel_requested -> cancelled
completed/failed/cancelled -> 不再变化
```

前端在 `cancel_requested` 时显示“正在停止当前模型调用后的后续步骤”。服务端保证：

- 不再启动新的修复或分片；
- 并发子任务收到取消；
- 未验证结果不落库；
- 已验证分片可保留到任务 TTL，便于诊断，但取消任务不能恢复为运行；
- campaign ID 预留及时释放。

## 8. 失败体验

公开错误使用稳定 `error_code`：

```text
story_plan_invalid
story_output_truncated
story_fragment_invalid
story_continuity_failed
story_provider_timeout
story_provider_busy
story_cancelled
story_internal_error
```

用户文案说明“发生在哪个公开阶段”和“是否适合重试”，不暴露具体线索、ID 或供应商详情。例如：

```text
故事结构在限定修复次数内仍未稳定。本次没有生成草稿，请重新提交；已确认的故事设计不会被修改。
```

## 9. 前端状态展示

- queued：显示队列位置和取消按钮；
- planning：显示“正在规划故事结构”；
- compiling：显示“正在编译可玩内容（3/8）”；
- repairing：显示“正在校正结构（第 1 次）”，不显示内部错误；
- validating：显示“正在执行规则校验”；
- continuity：显示“正在复核剧情连贯性”；
- completed：显示公开摘要和发布按钮；
- failed：显示可重试建议，保留确认稿；
- cancel_requested：禁用重复取消，继续轮询到终态。

页面刷新后继续使用本地保存的 task ID 恢复，不重新提交任务。

## 10. 测试要求

1. 两个 queued 任务返回正确的相对位置。
2. running 任务的 queue position 为 0。
3. 分片并发乱序完成时进度只增不减。
4. 修复阶段不伪造额外进度。
5. queued 任务可以立即取消并释放预留。
6. running 任务取消后不会启动新分片或重试。
7. API 响应不包含 Plan、Canon、NPC 秘密和模型详情。
8. 两个 worker 不会领取同一任务。
9. 前端刷新后能够恢复轮询。
10. 旧 `/drafts` 超时不会悄悄创建第二个任务。

## 11. 验收标准

- 用户能区分排队、生成、修复、校验和取消。
- 多任务排队时可看到位置，不再表现为无进度卡住。
- 进度以实际验证单元计算且不会回退。
- 官方前端不再依赖长连接 `/drafts`。
- 多 worker 上线前有全局并发上限和原子领取测试保护。
