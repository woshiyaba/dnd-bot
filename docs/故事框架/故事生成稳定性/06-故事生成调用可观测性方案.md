# 故事生成调用可观测性方案

> 文档状态：计划实施
> 设计基线：2026-08-03
> 单一问题：缺少阶段耗时、token、结束原因和错误收敛数据，无法定位慢请求和失败热点
> 目标文件：`src/story/generator.py`、`src/services/story_service.py`、`src/story/store.py`、`src/common/utils/llm_util.py`

## 1. 问题定义

当前日志能看到部分修复错误，但缺少每次模型调用的统一耗时、响应大小、token 和 `finish_reason`。StoryPlan 修复还会记录完整 Prompt，造成日志体积过大并暴露故事秘密。

本文只解决服务端观测，不定义前端进度展示。

## 2. 调用事件模型

建议所有故事模型调用产生统一事件：

```python
class StoryLLMCallEvent(BaseModel):
    event_id: str
    task_id: str | None
    stage: str
    unit_kind: str
    unit_id: str | None
    attempt_kind: Literal["initial", "transport", "parse_recovery", "repair", "replan"]
    attempt_index: int
    model_role: str
    model_name: str
    started_at: datetime
    elapsed_ms: int
    prompt_chars: int
    response_chars: int
    input_tokens: int | None
    output_tokens: int | None
    finish_reason: str | None
    outcome: Literal["success", "timeout", "provider_error", "parse_error", "validation_error", "cancelled"]
    validation_issue_count: int = 0
    error_fingerprint: str | None = None
```

事件不包含 Prompt、原始响应、NPC 秘密、用户完整输入或凭据。

## 3. 记录位置

固定在模型调用网关记录开始和结束，避免每个生成函数自行拼日志。业务校验完成后再补充：

- `validation_issue_count`；
- `error_fingerprint`；
- 本次候选是否触发代码归一化；
- 修复单元是否升级。

可以先使用结构化日志，稳定后再增加 SQLite `generation_call_events` 表。不要在主任务表反复追加大 JSON。

## 4. Stage 计时

除单次调用外，还要记录阶段跨度：

```text
queue_wait
planning
plan_repair
fragment_wave_a
fragment_wave_b
assembly_validation
continuity_review
continuity_repair
total
```

并发分片阶段的总耗时不能简单累加各调用耗时；需要同时记录：

- wall-clock duration；
- 各分片 duration；
- 最大并发；
- semaphore 等待时间。

## 5. 日志规范

推荐单行结构化日志：

```text
[story_llm] task=... stage=fragment unit=act:act_2 attempt=repair:1
model=... elapsed_ms=... prompt_chars=... response_chars=...
finish_reason=stop outcome=validation_error issue_count=3 fingerprint=...
```

禁止：

- 默认打印完整系统 Prompt；
- 打印完整 StoryPlan、Canon 或确认稿；
- 打印 API key、Authorization、base URL 查询参数；
- 把供应商原始异常不经脱敏直接返回用户。

调试环境如确需原文，使用显式开关、受限目录、文件权限和自动过期，并在文件名中使用随机事件 ID。

## 6. 核心指标

### 6.1 延迟

- 各 stage P50/P90/P99；
- 各 ModelRole 首次成功耗时；
- queue wait 与执行时间占比；
- 单故事 wall-clock 总时长。

### 6.2 稳定性

- 首次 JSON 解析成功率；
- 首次业务校验通过率；
- 平均修复次数；
- 重复错误指纹提前终止次数；
- 各 `issue.code` 出现频率；
- continuity 一次通过率。

### 6.3 成本与容量

- 每个 story 的输入/输出 token；
- 每类修复 token；
- 并发信号量等待时间；
- 429、timeout、供应商错误率。

## 7. 告警建议

- StoryPlan 单次调用超过历史 P99；
- `finish_reason=length` 比例持续升高；
- 同一 issue code 一小时内集中出现；
- 首次校验通过率低于基线；
- queue wait 超过执行时间；
- 单任务 token 或修复次数超过预算。

告警只包含 task ID、stage 和错误码，详细内容通过受控诊断查询获取。

## 8. 数据保留

- 任务阶段和聚合指标可随任务保留 24 小时。
- 调用事件建议保留 7～14 天，按部署容量调整。
- 原始 Prompt/响应默认不保存。
- 草稿和调用指标采用不同 TTL，发布故事不应永久携带生成诊断数据。

## 9. 测试要求

1. 成功、解析失败、业务失败和取消都会产生结束事件。
2. 事件中不包含 API key、URL、完整 Prompt 或完整响应。
3. 并发分片能正确记录 wall-clock 和单分片耗时。
4. token 元数据缺失时字段为 null，不影响业务。
5. 错误指纹稳定且不包含故事文本。
6. 日志失败不能导致故事任务失败。
7. stage 总时长和调用事件能够通过 task ID 关联。

## 10. 验收标准

- 能明确回答“慢在排队、Plan、哪个分片、修复还是连贯性”。
- 能明确回答输出是否因 token 上限被截断。
- 能按 issue code 找出最常见校验失败。
- 生产日志不再出现完整 StoryPlan 修复 Prompt。
- 可用真实数据决定并发、模型和输出预算，而不是继续猜测。
