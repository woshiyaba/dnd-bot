# 故事生成重试预算与模型调用治理方案

> 文档状态：计划实施
> 设计基线：2026-08-03
> 单一问题：不同失败类型共享过高的修复上限，模型、输出预算和超时也没有按职责配置
> 目标文件：`src/story/generator.py`、`src/common/utils/llm_util.py`、`.env.example`

## 1. 问题定义

当前 `MAX_REPAIR_ATTEMPTS=10` 同时影响 StoryPlan 和 Canon 分片。一次大 JSON 修复可能耗时很长，10 次上限会把单个无法收敛的问题放大成极端等待。代码中的错误文案和现有设计文档仍写“两次”，实际策略不一致。

模型注册目前只配置模型名称、base URL 和 API key，没有按职责设置输出上限、超时、采样参数或应用层重试预算。

本文只定义调用和重试预算，不重复定义 JSON、Plan 或分片的具体修复内容。

## 2. 重试类型必须拆分

```python
@dataclass(frozen=True)
class StoryRetryPolicy:
    transport_attempts: int
    parse_recovery_attempts: int
    validation_repair_attempts: int
    structural_replan_attempts: int
```

建议首版预算：

| 阶段 | 传输重试 | JSON 恢复 | 业务修复 | 结构重规划 |
| --- | ---: | ---: | ---: | ---: |
| StoryPlan | 1 | 1 | 2 | 1 |
| 普通分片 | 1 | 1 | 2 | 0 |
| 局部条目修复 | 1 | 1 | 1 | 0 |
| 连贯性复核 | 1 | 1 | 0 | 0 |
| 连贯性定向修复 | 1 | 1 | 1 | 0 |

表中数字是“初次调用之后允许的额外次数”。任何阶段都不能再隐式继承全局 10 次。

模型 SDK 自带的网络重试必须纳入同一传输预算，不能出现“SDK 内重试两次，应用层又重试一次”却只统计为一次的情况。实现时应关闭一侧重试，或让调用网关读取并汇总 SDK 的真实尝试次数。

## 3. 不收敛提前终止

业务修复每轮计算错误指纹：

```text
fingerprint = hash(sorted((issue.code, issue.path, issue.object_id)))
```

满足任一条件立即停止当前修复模式：

- 连续两轮指纹完全相同；
- 错误数量增加；
- 本应局部修复却出现新的结构错误；
- 模型连续两次修改白名单外字段；
- 剩余错误要求改变当前修复模式禁止修改的对象。

停止后按策略升级到更大修复单元或显式失败，不能继续机械消耗剩余次数。

## 4. 按职责配置模型参数

建议给 `ModelConfig` 增加职责调用配置，环境变量可使用统一前缀：

```text
STORY_PLANNING_MAX_OUTPUT_TOKENS
STORY_PLANNING_TIMEOUT_SECONDS
STORY_AUTHORING_MAX_OUTPUT_TOKENS
STORY_AUTHORING_TIMEOUT_SECONDS
STORY_REPAIR_MAX_OUTPUT_TOKENS
STORY_REPAIR_TIMEOUT_SECONDS
STORY_CONTINUITY_MAX_OUTPUT_TOKENS
STORY_CONTINUITY_TIMEOUT_SECONDS
STORY_FRAGMENT_CONCURRENCY
```

不要在文档中固定某家供应商的具体 token 数。应先根据不同 length mode 的真实输出分布配置：

```text
short: P99 输出 token + 20% 余量
standard: P99 输出 token + 20% 余量
long: P99 输出 token + 20% 余量
```

若模型 SDK 支持 per-call bind，按 stage 绑定参数；不要因为同一个物理模型被多个职责复用，就强制共享一个输出上限。

## 5. 模型分层

| 工作 | 默认模型层级 | 说明 |
| --- | --- | --- |
| StoryPlan 初稿和结构重规划 | reasoning | 需要处理全局图、节奏和 owner |
| Canon 创作载荷 | reasoning | 需要剧情与规则一致性 |
| 单纯 JSON 格式恢复 | fast | 只恢复语法，不改业务事实 |
| 枚举或单字段组修复 | fast，失败后升级 reasoning | 输入小、契约封闭 |
| 单 Beat 语义联动修复 | reasoning | 涉及线索、战斗和推进条件 |
| 连贯性复核 | reasoning | 需要全局语义判断 |

快速模型修复结果仍需相同校验，不因模型层级降低而放宽规则。

## 6. Prompt 预算

每个修复 Prompt 只携带当前修复单元及其直接依赖。禁止默认重复发送：

- 完整 StoryPlan schema；
- 完整确认稿的无关字段；
- 两份完整参考 Canon；
- 已验证且与错误无关的其它分片；
- 多轮完整失败输出。

保留最近两轮错误时，只携带错误指纹和简短结构化摘要，不携带完整旧 Prompt。

## 7. 超时策略

- 连接和读取超时由模型客户端配置。
- 应用层为每个 stage 设置总 deadline，覆盖内部所有重试。
- 用户取消优先于下一次重试；检查取消标记后才能再次调用模型。
- 超时后不确定供应商是否仍执行请求，因此同一 stage 使用 `attempt_id` 做幂等追踪。
- 达到 deadline 时返回明确的阶段错误，不继续进入业务修复。

## 8. 测试要求

1. Plan 和分片不再共享同一个全局修复次数。
2. 错误指纹重复时提前终止。
3. 网络重试不计入业务修复次数。
4. JSON 恢复不计入业务修复次数。
5. 不同 ModelRole 能绑定不同 timeout 和输出预算。
6. fast 局部修复失败后最多升级 reasoning 一次。
7. 用户取消后不再执行下一次重试。
8. 代码、错误文案和文档中的预算保持一致。

## 9. 验收标准

- 删除 `MAX_REPAIR_ATTEMPTS=10` 这一跨阶段全局策略。
- 任一生成单元的业务修复不超过 2 次。
- 重复错误不会继续调用模型。
- 能从指标中区分传输、解析、业务和结构重规划次数。
- timeout 和输出预算可以按职责及故事档位配置。
