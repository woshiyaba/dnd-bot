# 长篇与多流程故事生成优化方案

> 文档状态：后续优化设计
> 评审基线：2026-07-31
> 目标文件：`src/story/prompt.py`
> 关联实现：`src/story/generator.py`、`src/model/canon.py`、`src/session/`、故事工作台前端
> 本文先给出设计，不直接修改当前 Prompt 和 Canon wire format。

## 一、核心结论

如果目标只是把当前 20 分钟冒险稍微加长到 30～45 分钟，可以在同步修改校验器后，通过 Prompt 增加 Beat 数量、节奏比例和分支约束完成第一版。

如果目标是稳定生成 60～120 分钟、8～12 个可玩 Beat、多个调查/冲突流程的故事，**只改 `CANON_AUTHORING_RULE` 的一句“故事更长”不够**。当前生成方式会遇到四个结构性瓶颈：

1. Prompt 和校验器把时长硬限制为 10～30 分钟。
2. 两份参考 Canon 都是 5 拍，模型会强烈模仿这个规模。
3. 完整 Canon 一次性生成，长篇时容易输出截断、ID 漂移和引用错误。
4. 运行时只保留最近 6 条对话，长篇中的关系、承诺和支线缺少结构化长期记忆。

推荐把故事生产流程升级为：

```text
访谈 DesignBrief
  -> Pro 生成 StoryPlan
  -> 确定性校验计划
  -> 按 Act/Beat 分段编译
  -> 汇总 Canon
  -> 完整结构校验
  -> 定向修复
  -> Pro 连贯性复核
  -> 发布
```

StoryPlan 是生成阶段的中间产物，可以最终扁平化为现有 `beats`，因此第一版不一定要给运行时 Canon 增加 `acts` 字段。

## 二、当前限制在哪里

### 2.1 明确的 10～30 分钟硬限制

`src/story/prompt.py` 中至少有三层限制：

- `STORY_INTERVIEW_RULE` 的示例默认时长是 20 分钟；
- `CANON_AUTHORING_RULE` 明确写着“一局是 10～30 分钟的短篇冒险”；
- `validate_confirmed_design_brief()` 拒绝 10～30 之外的时长。

`src/model/canon.py:validate_canon()` 又会拒绝 10～30 之外的 `duration_minutes`。因此只改 Prompt 文案，生成的长篇 Canon 仍会在确定性校验阶段失败。

需要协同修改：

```text
src/story/prompt.py
src/model/canon.py
test/test_canon_authoring_prompt.py
test/test_story_api.py
故事工作台相关前端文案与选项
```

### 2.2 参考样例形成固定 5 拍偏置

两份内置参考都是 5 拍：

```text
opening
  -> exploration
  -> climax
  -> ending_win / ending_lose
```

Prompt 虽然没有硬编码“只能 5 拍”，但模型会从完整样例中学习规模。要生成更多流程，需要：

- 在设计稿中显式给出目标 Beat 范围；
- 给长篇模式提供长篇结构范式，而不是继续完整塞入两个短篇；
- 把“结构参考”和“剧情内容参考”分离；
- 校验实际 Beat 数量是否符合确认的规模。

### 2.3 单次 Prompt 已经很大

在使用最小确认设计稿时，当前构造结果约为：

| 内容 | 字符数 |
| --- | ---: |
| `CANON_AUTHORING_RULE` | 8,979 |
| 两份压缩参考 Canon | 18,067 |
| 完整 authoring prompt | 27,674 |

这还没有计算真实玩家设计稿和模型输出。长篇 Canon 若一次生成，输入规则、参考和输出会同时膨胀，模型更容易：

- 在输出后半段丢字段；
- 重复或改写 ID；
- 忘记前面定义的 owner；
- 把某拍的 NPC、线索或 Encounter 引到错误位置；
- 因输出上限截断成不可解析 JSON。

### 2.4 当前 Canon 校验只保证部分结构合法

现有校验的优点是能检查大量 ID、白名单、引用和 owner 问题，但它没有保证：

- Beat 数量与时长匹配；
- 每条可选路径最终都能到达结局；
- 不存在永远循环的分支；
- 分支在合理范围内重新汇流；
- 线索有冗余取得路径或 fail-forward；
- 每一幕都有推进、升级和回收；
- 多结局会按玩家选择正确路由；
- 战斗难度随玩家人数合理变化。

因此“校验通过”和“流程足够多且好玩”是两件事。

## 三、先定义可执行的规模档位

不要让模型根据“长一点”自由猜规模。建议在 DesignBrief 中使用明确的 `length_mode` 和 `scale_profile`。

| 档位 | 总时长 | 可玩 Beat，不含结局 | 地点总数 | 遭遇数 | 关键线索 | 分支要求 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| short | 10～30 分钟 | 3～4 | 3～5 | 1～2 | 2～4 | 可线性，至少有玩法选择 |
| standard | 31～60 分钟 | 5～7 | 5～8 | 2～3 | 4～7 | 至少 1 个分支并在高潮前汇流 |
| long | 61～120 分钟 | 8～12 | 8～14 | 3～5 | 7～12 | 至少 2 个有后果的分支，控制汇流 |
| campaign | 120 分钟以上或多 session | 分章节生成 | 分章节 | 分章节 | 分章节 | 必须先完成持久化与分章加载 |

这些数字是生产约束的起点，不是永远固定的游戏设计。后续应根据真实玩家的每拍用时和空转回合调整。

建议把时长拆成节奏预算：

```text
开场与钩子：10%～15%
调查/探索/社交：40%～50%
升级冲突与转折：15%～25%
高潮：15%～20%
结局与回顾：5%～10%
```

模型必须根据预算分配 Beat，而不是简单重复三个相似探索场景。

## 四、扩展 DesignBrief

当前设计稿只有总时长、玩法侧重和结局方向，无法约束长篇结构。建议增加：

```json
{
  "length_mode": "long",
  "duration_minutes": 90,
  "target_sessions": 1,
  "target_beat_count": 10,
  "act_count": 4,
  "branching_style": "branch_and_reconverge",
  "branching_budget": {
    "meaningful_branch_points": 2,
    "max_parallel_beats": 2,
    "reconverge_before_climax": true
  },
  "pacing": {
    "opening_percent": 10,
    "exploration_social_percent": 45,
    "escalation_percent": 20,
    "climax_percent": 20,
    "ending_percent": 5
  },
  "set_pieces": ["必须出现的重大场景"],
  "side_content": {
    "desired_side_threads": 2,
    "must_resolve_before_ending": true
  },
  "failure_style": "fail_forward_with_cost",
  "replayability": "medium"
}
```

### 4.1 访谈阶段要新增的问题

只有在玩家没有表达时才询问：

1. 想玩一局完成，还是分多次 session？
2. 希望路线偏线性、有限分支，还是明显多路线？
3. 更长的时间主要用于调查社交、战斗、旅行，还是角色关系？
4. 支线是否必须在结局前收束？
5. 玩家能接受多大的失败代价与不可逆选择？

仍然保持“每轮最多三个问题”，不要把长篇配置变成一次性表单。

### 4.2 最终确认摘要必须展示规模

`ready_for_confirmation` 的摘要应明确写出：

- 预计时长与 session 数；
- 预计 Act 和可玩 Beat 数；
- 主要分支数及是否汇流；
- 预计遭遇数；
- 支线数量；
- 结局数量和方向。

玩家确认的是一份可量化规模契约，而不只是主题描述。

## 五、增加 StoryPlan 中间阶段

### 5.1 为什么要先生成计划

完整 Canon 同时包含叙事设计、ID 注册、战斗卡面、规则行动和大量交叉引用。把这些都放在一次生成中，会让模型同时承担创作与编译器工作。

StoryPlan 先解决“故事是否成立”，Canon 编译再解决“引擎如何表示”：

```text
StoryPlan：剧情结构、节奏、因果、分支、线索图
Canon：字段、ID、卡面、Trigger、ActionDefinition、引用闭合
```

### 5.2 建议的 StoryPlan 形状


StoryPlan 不是运行时 JSON，不受当前 Canon schema 限制。其作用是给后续分段编译提供稳定的全局 ID、因果和 owner 账本。

### 5.3 计划阶段的确定性校验

在开始生成详细 Canon 前，至少检查：

- Beat 数量和预计分钟数符合 scale profile；
- Act 的预计分钟数总和与总时长一致；
- 所有 Beat 从起点可达；
- 从每个非结局 Beat 都至少存在一条通向结局的路径；
- 强连通环不能成为无出口死循环；
- 分支数量、最大并行宽度和汇流点符合预算；
- 每个硬门槛有至少两种世界内处理方式或一条带代价的 fail-forward；
- Clue、Flag、Item 和 Action 的 owner 唯一；
- 每个伏笔在后续有回收位置；
- 遭遇和高潮密度符合玩法侧重。

计划不通过时只修计划，不要浪费一次完整 Canon 生成。

## 六、分段编译 Canon

### 6.1 推荐拆分

建议按下面顺序生成：

1. 顶层元数据、全局胜负方向、ID registry；
2. Cast 与 CombatCard；
3. Locations；
4. 每个 Act 或每组 2～3 个 Beat；
5. ActionDefinition；
6. 汇总与完整校验。

每个分段 Prompt 都携带：

- 已确认 DesignBrief；
- 已校验 StoryPlan；
- 不可改写的全局 ID registry；
- effect owner ledger；
- 当前要生成的片段；
- 当前片段真正需要引用的前后 Beat；
- 已生成片段的结构摘要，而不是整份全文。

### 6.2 不要让分段生成创造新全局 ID

分段模型只能使用 StoryPlan 注册过的 ID。确实缺少 ID 时，应返回结构化错误回到计划阶段，不允许某个 Beat 临时发明新 NPC、Flag 或 Item。

### 6.3 汇总后仍需完整校验

分段合法不代表汇总合法。最终必须重新运行：

- `Canon.from_dict()`；
- `validate_canon()`；
- `validate_authored_canon()`；
- 新增的规模、路径终止、分支和节奏校验；
- Pro 连贯性复核。

Pro 连贯性复核只报告问题，不直接绕过确定性校验提交世界状态。

## 七、`src/story/prompt.py` 的具体优化方向

### 7.1 修改 `STORY_INTERVIEW_RULE`

在“必须由玩家确认的大方向”中加入：

```text
【规模与结构】
- 确认 length_mode、总时长、是否跨 session，以及目标可玩 Beat 范围。
- 确认路线是线性、有限分支后汇流，还是多路线。
- 确认更长的篇幅主要分配给哪类玩法，不能只重复相似场景。
- 确认支线数量、是否必须收束，以及结局对分支的回应程度。
```

在结构化 `design_brief` 中加入第四节列出的字段，并把这些字段纳入 `_REQUIRED_CONFIRMED_FIELDS` 或独立的严格 `StoryDesignBrief` schema。

不要继续使用任意 `dict[str, Any]` 作为最终设计稿的唯一边界。

### 7.2 替换固定“短篇设计目标”

当前：

```text
一局是 10～30 分钟的短篇冒险……
```

建议改为：

```text
【规模契约】
- 必须原样采用 confirmed_design_brief.scale_profile。
- Beat、地点、遭遇、线索与分支数量必须落在对应档位范围内。
- 可玩 Beat 不包含 ending；不得用增加多个空结局来凑 Beat 数。
- 每个 Beat 必须承担不同的剧情功能：建立、发现、选择、升级、代价、回收或高潮。
- 禁止连续生成只更换地点名、实际目标和推进方式相同的填充 Beat。
- 每个 Beat 填写可执行目标、压力来源、至少一个状态变化，以及离开本拍的明确条件。
```

### 7.3 增加长篇节奏规则

```text
【长篇节奏】
- opening 在前 15% 内完成钩子与角色动机。
- 中段每 2～3 个 Beat 至少发生一次信息反转、关系变化、资源代价或威胁升级。
- 支线必须改变 Flag、Item、NPC 关系、战斗优势或结局反馈，纯装饰支线不进入 Canon 主流程。
- 高潮前必须回收主要调查线索，但不要把全部答案一次性由 NPC 口述。
- 结局必须逐项回应玩家形成的关键状态，不得只复述“击败 Boss”。
```

### 7.4 增加分支和汇流规则

```text
【分支预算】
- 分支数量必须符合 branching_budget，不得无限扩张。
- 两条路线必须至少在地点、遭遇、获得的信息、资源代价或 NPC 后果之一真正不同。
- 建议在 1～2 个 Beat 后汇流，汇流时保留各路线产生的 Flag/Item/关系差异。
- 分支汇流不是抹掉选择；后续叙述、可用行动或结局必须读取已形成的差异。
- 每个分支节点都必须有 stuck_fallback 和可继续的失败路径。
```

### 7.5 限制 `semantic` Trigger

长篇 Beat 越多，`semantic` 越多，每个回合越可能产生额外 LLM 调用和错误推进。Prompt 应新增：

```text
【Trigger 选择优先级】
1. 能由 flag/item/location/combat_outcome/action 表达时，禁止使用 semantic。
2. 每个 Beat 默认最多一个 semantic 条件。
3. semantic.prompt 必须是只依据已经发生事实即可回答的稳定是/否问题。
4. 不得用 semantic 判断 HP、物品、地点、战斗胜负或已经有结构化 Flag 的事实。
```

### 7.6 使用 Rule of Three，但不破坏唯一 owner

关键事实最好有三种可接近方式，但当前 `validate_authored_canon()` 要求每个持久化 Flag/Item 只有一个原子写入 owner。正确表达是：

- 同一个 `KeyInfo` 是唯一发现 owner；
- 玩家可以通过交谈、搜索、潜行、战斗后搜身等不同方式接近这个发现；
- 或者创建三个不同 Clue/Flag，推进条件使用 `any`；
- 不要让三个 KeyInfo 重复发放同一个 Item 或写同一个 Flag。

Prompt 可写：

```text
每个主线硬门槛至少提供两种可执行接近方式和一种带代价的失败前进方式。
多种方式可以汇入同一个唯一 discovery owner；若使用多个独立线索，则分别写入不同 Flag，
再由 any 条件判断，不得违反持久化效果唯一 owner。
```

### 7.7 更新提交前自检

在现有十项基础上增加：

1. Beat 数量、Act 数量和预计时长符合 scale profile。
2. 每个非结局 Beat 都能沿至少一条路径到达某个结局。
3. 不存在无退出的剧情循环。
4. 分支数、并行宽度和汇流点符合 branching budget。
5. 连续 Beat 不得有相同目标、相同推进方式和相同后果。
6. 每个主要伏笔、支线和 NPC 关系在后续有回收点。
7. 每个硬门槛都有替代办法或 fail-forward。
8. `semantic` 数量受控，能确定性表达的条件不得使用 semantic。
9. 关键选择会形成后续可读取的 Flag、Item、关系或结局反馈。
10. 最长路径和最短路径的预计时长都在玩家确认范围内。

## 八、修复 Prompt 需要重做

当前 `build_canon_repair_prompt()` 只携带：

- 校验错误；
- 当前 Canon 草稿。

它没有重新携带完整的 confirmed DesignBrief、内容边界、StoryPlan、ID registry 和完整创作规则。模型在修复结构时可能顺便改写主题、敏感内容边界或分支规模。

建议修复输入至少包含：

```text
<immutable_design_brief>
<validated_story_plan>
<immutable_id_registry>
<effect_owner_ledger>
<validation_errors>
<affected_fragments>
<canon_draft>
```

并区分三种修复：

1. **机械修复**：重复 ID、漏引用、枚举、字段类型，优先由代码完成。
2. **局部模型修复**：只返回受限 patch，应用后重新完整校验。
3. **结构重规划**：路径、节奏、线索因果错误，退回 StoryPlan 阶段用 Pro 修改，再重新编译受影响 Act。

不要让一次局部错误触发整份长篇 Canon 的自由重写。

## 九、多流程与多结局的运行时限制

### 9.1 多个同类结局目前不能可靠自动选择

当前 `Canon.ending_beat(outcome)` 返回第一个匹配的胜利或失败结局；`evaluate_advancement()` 又先检查全局 `win_condition / lose_condition`。如果生成多个 `ending_outcome=win`，全局胜利命中时通常会直接进入第一个胜利结局，无法根据路线自动选择其它胜利结局。

在引擎扩展前，Prompt 应只生成一个权威 win ending 和一个 lose ending，路线差异写进结局叙述和状态回顾。

若要真正支持多结局，需要改造为类似：

```json
{
  "ending_routes": [
    {
      "trigger": {"kind": "flag", "predicate": {"flag": "saved_spirit"}},
      "ending_beat_id": "ending_redemption",
      "priority": 100
    }
  ]
}
```

并由引擎按明确优先级确定性选择，而不是让 LLM 临场挑结局。

### 9.2 一个 Beat 只有一个预置 Encounter

当前 `Beat.encounter` 是单值。一个长篇 Beat 若需要多个独立战斗，不能只靠 Prompt 塞入数组。第一版应拆成多个 conflict Beat；若确实要在同一沙盒 Beat 内支持多个遭遇，则需要先扩 Canon schema、运行时状态和校验器。

### 9.3 `recommended_player_count` 只是展示字段

当前人数不会自动缩放敌人 HP、数量、伤害或 DC。长篇 Prompt 即使写“支持 1～6 人”，生成的静态卡面也可能只适合一种队伍规模。

需要选择：

- 每个 Canon 固定一个推荐人数范围并明确测试；
- 或增加 encounter scaling profile，由引擎按实际队伍人数确定性调整。

不能让运行时 LLM 自由修改 HP/AC/伤害来平衡。

## 十、长篇运行时记忆

### 10.1 当前上下文不足

DM 每回合只看到最近 6 条消息，以及当前 Beat、所有已发现线索和 Flag。对于长篇，容易忘记：

- 玩家答应过某个 NPC 的事情；
- NPC 对玩家的信任、恐惧或敌意变化；
- 尚未解决的支线；
- 玩家采用过的道德立场；
- 多个 Beat 前留下的非线索伏笔。

### 10.2 建议的结构化长期记忆

在规则状态中增加或派生：

```json
{
  "open_threads": [],
  "resolved_threads": [],
  "npc_relationships": {},
  "important_choices": [],
  "promises": [],
  "act_recap": "",
  "relevant_fact_ids": []
}
```

重要事实仍由 Flag、Item、事件和关系枚举确定性保存。`act_recap` 可以由 Fast 模型在进入新 Act 时生成，但必须能从结构化事件重新构建，不能反过来覆盖规则状态。

### 10.3 控制上下文增长

- `known_clues` 不应永远全量下发，应由当前 Beat 的 `relevant_clue_ids` 选择。
- 最近消息保留 6～10 条，同时加入当前 Act 的结构化 recap。
- `campaign_log` 持久化并分页，checkpoint 只保留必要工作集或引用。
- `SessionView.timeline` 改成 cursor 分页或 WebSocket 增量，不要每个回合返回全量历史。

## 十一、两个可执行落地方案

### 方案 A：最小改造，先支持 45～60 分钟

适合快速验证：

1. 将时长上限从 30 调到 60，并同步所有校验与测试。
2. DesignBrief 增加 `length_mode`、`target_beat_count`、`branching_style`。
3. Prompt 要求 5～7 个可玩 Beat，加 2 个结局 Beat。
4. 增加节奏、分支汇流、Trigger 优先级和 fail-forward 规则。
5. 仍用 Pro 一次生成完整 Canon，但设置明确输出预算。
6. 保持一个 win ending 和一个 lose ending。
7. 用 20 份固定 DesignBrief 测输出截断率和校验修复率。

风险：规模继续增加时仍会撞到单次输出和整稿修复瓶颈。

### 方案 B：推荐方案，支持 60～120 分钟

1. 严格 DesignBrief。
2. Pro 生成 StoryPlan。
3. 新增计划校验器。
4. 按 Act/Beat 分段编译。
5. 全局 ID registry 和 effect owner ledger 锁定引用。
6. 局部 patch 修复。
7. 增加长局结构化记忆与 timeline 分页。
8. 持久化 room、draft、checkpoint 和生成任务。
9. 用 Pro 做最终连贯性报告，确定性校验决定能否发布。

这是避免 Prompt 越写越长、模型仍然不稳定的根本方案。

## 十二、建议的实现顺序

### 第 1 步：建立长篇测试基线

- 准备 short、standard、long 各 10 份确认 DesignBrief。
- 记录输出字符数、解析成功率、首次校验通过率、修复次数和生成时间。
- 增加最长/最短路径、Beat 数和 semantic 数量统计。

### 第 2 步：严格设计稿与规模校验

- 新增 `StoryDesignBrief` schema。
- 同步前端字段和确认摘要。
- 修改 10～30 分钟硬限制。
- 增加 scale profile 校验。

### 第 3 步：先改 Prompt 结构

- 加入规模契约、节奏、分支、fail-forward 和 Trigger 优先级。
- 暂时维持单次 Canon 生成，验证 45～60 分钟上限。
- 减少完整参考 Canon，改用结构片段或按档位选择参考。

### 第 4 步：引入 StoryPlan

- 定义 StoryPlan schema。
- 增加计划生成、校验、确认和持久化。
- 再实现分段 Canon 编译。

### 第 5 步：补运行时长局能力

- 持久化 checkpoint 和房间；
- session 级骰子；
- 幂等命令；
- 长期记忆；
- timeline 分页；
- 多结局确定性路由。

## 十三、验收标准

### 结构指标

- `long` 档实际生成 8～12 个可玩 Beat，不靠结局凑数。
- 每个非结局 Beat 至少存在一条到结局的路径。
- 不存在无出口循环。
- 分支和汇流符合 DesignBrief。
- `semantic` trigger 数量不超过约定预算。
- 所有 ID、引用和原子 owner 校验通过。

### 体验指标

- 不同 Beat 的目标、压力和结果可被玩家区分。
- 中段每 2～3 个 Beat 有可观察的局势升级或反转。
- 支线会改变规则状态或结局反馈。
- 玩家能说出至少两个早期选择如何影响后续。
- 最短路线和最长路线的实际时长都在确认范围附近。

### 生成质量指标

- JSON 截断率；
- 首次解析成功率；
- 首次完整校验通过率；
- 平均修复次数；
- 修复后 DesignBrief 漂移率；
- 单个故事的输入/输出 token、耗时与费用；
- Pro 连贯性报告中的严重问题数。

长篇生成的关键不是要求模型“多写几个场景”，而是先把规模、节奏、分支和因果变成可校验的结构，再让模型分阶段填充内容。这样 Prompt 才是在约束一个编译过程，而不是祈祷一次超长输出刚好完整。


  - 当前 Canon authoring prompt 在加入真实设计稿前已约 27,674 字符。建议升级为“DesignBrief → StoryPlan → 分段编译 → 定向修复”，避免长输出截断和引用漂移。

  同时记录了结构化输出静默纠正、"false" 可能被判真、无鉴权故事生成接口、内存存档、请求无幂等、全局骰子、长局上下文增长及遗留 /invoke 等问题。
