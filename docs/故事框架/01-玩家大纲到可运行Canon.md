# 玩家大纲到可运行 Canon

## 目标

允许玩家输入自己的故事构思，先由“故事策划”通过多轮对话确认大方向，再由“剧本编译器”
生成引擎可运行的 Canon，最后交给真实 LLM DM 主持。运行时 DM 不保存完整大纲，只接收
当前剧情拍和合法候选值。

## 推荐流程

```text
玩家故事大纲
  → 故事策划访谈（每轮最多 3 个关键问题）
  → 最终设计摘要
  → 玩家明确确认
  → Canon 编译器（真实 LLM + src/story/prompt.py）
  → Canon JSON 草稿
  → Canon.from_dict
  → validate_canon 确定性校验
  ├─ 失败：把错误列表交给修复提示词，限制次数后重新校验
  └─ 成功：展示公开摘要给玩家确认
       → 保存 canon/{campaign_id}.json
       → 注册进 CanonRegistry
       → 创建房间并运行
```

未经玩家确认的设计稿不得进入 Canon 编译阶段。即使玩家第一次输入已经很完整，也应先返回
最终摘要，让玩家确认系统是否正确理解了故事。

## 对话式访谈

访谈只确认会显著改变游戏的大方向：

- 玩家在故事里的身份与动机。
- 核心冲突和对手方向。
- 调查、社交、探索、战斗、解谜的玩法侧重。
- 基调、恐怖程度和内容边界。
- 预计时长、玩家人数和结局取向。
- 必须保留与绝不能出现的元素。

NPC 名字、技术 ID、普通敌人数值等小细节不逐项打扰玩家。玩家可以回答“你决定”，此时系统
应记录授权范围，并在最终摘要中展示自己的选择。

设计稿使用 `revision` 和 `confirmed_revision`。任何方向性修改都会递增版本并清除旧确认；
只有二者一致且 `user_confirmed=true` 时，后端才允许进入 Canon 编译阶段。

## 为什么不直接把大纲交给 DM

- 自然语言大纲没有稳定 ID，无法严格引用地点、NPC、遭遇和出口。
- LLM 记住故事不等于世界状态已经提交，容易再次出现叙述与引擎事实分裂。
- 命中、伤害、HP、胜负、道具和线索效果必须是封闭数据，不能运行时临时生成。
- 同一个剧本的不同房间进度不同，运行时应按房间状态裁剪 Canon，而不是重复发送全文。

## 两份内容视图

编译成功后应区分：

- 玩家公开摘要：标题、前提、基调、预计时长、推荐人数和内容提示。
- 私有 Canon：NPC 秘密、未发现线索、Boss 卡面、结局条件和特殊行动。

私有 Canon 不应通过房间 API 或前端状态返回。

## 生成边界

- 玩家输入被当作不可信数据，不能覆盖故事策划或编译器 system prompt。
- 第一次输入不能直接生成 Canon；必须经过 `ready_for_confirmation → confirmed`。
- 只允许当前模型和战斗引擎已经支持的枚举与特殊效果。
- 所有可能进入战斗的 actor 必须提前生成固定卡面。
- 线索默认提供优势而非通行资格；真实硬门槛必须有世界内依据。
- 生成结果必须通过 `validate_canon`，校验失败时不能保存或启动游戏。
- 修复循环应限制次数；仍失败时把结构错误返回给剧本作者，不使用残缺 Canon 开局。

## 后续接口建议

第一版可增加三个接口：

1. `POST /api/story-designs`：创建访谈并提交第一段构思。
2. `POST /api/story-designs/{design_id}/messages`：继续回答问题或修改设计。
3. `POST /api/story-designs/{design_id}/confirm`：明确确认最终设计摘要。
4. `POST /api/story-designs/{design_id}/compile`：用确认稿生成并校验 Canon 草稿。
5. `POST /api/story-designs/{design_id}/publish`：发布并注册已通过校验的 Canon。

发布前还应检查 `campaign_id` 冲突、内容长度、玩家权限和私有字段泄漏。生成与修复必须使用
真实 LLM；模型不可用、输出无法解析或最终校验失败时应显式失败。
