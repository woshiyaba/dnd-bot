# 会话最终叙述统一方案

## 背景

当前会话主图的玩家输入处理链路是：

```text
dm_turn
  -> narrate_reply / narrate_result 先生成一段玩家可见 DM 文本
  -> evaluate_advancement 判断是否推进剧情拍
  -> enter_beat 切换 scene
  -> narrate_beat 再生成一段新拍过场
  -> END
```

当一次玩家输入同时触发“普通回应”和“剧情推进”时，会出现两段 DM 叙述：

- 第一段来自 `dm_turn` 内部的 `narrate_reply`，基于旧场景回应玩家动作。
- 第二段来自 `narrate_beat`，基于新场景描述切拍后的状态。

最终 payload 的 `say` 由 `SessionEngine._last_dm_say()` 从 `state.messages` 中取最后一条 DM 消息，因此 `say` 会变成第二段新拍叙述；而 `campaign_log` 中仍有第一段普通叙述。对用户来说，一次输入像是收到了两次回复，并且上下文跳跃。

## 目标

1. 一次玩家输入最多生成一条玩家可见 DM 消息。
2. `say`、`state.messages[-1]`、最后一条 `campaign_log[event=narration]` 保持一致。
3. DM 决策、规则结算、故事推进仍分层清晰：
   - DM 决策负责意图、检定规格、遭遇规格、叙述计划。
   - 引擎负责检定、战斗、剧情拍推进。
   - 最终 DM 叙述节点负责把本回合结果讲给玩家。
4. 不重新进入完整 `dm_turn` 子图，避免重复裁定、重复世界写入、重复中断或重复战斗。
5. 保持 WebSocket 流式体验：最终叙述仍通过 `dm_narrate()` 逐 token 推送。

## 非目标

- 不改变前端 WebSocket 协议。
- 不改变 `interrupt()` / `Command(resume=...)` 的交互模型。
- 不让 LLM 计算命中、伤害、HP、检定成败。
- 不增加 mock DM、模板叙述或 LLM 失败兜底。

## 核心思路

把“玩家可见叙述”从各个中间节点后移到主图末尾，由一个统一节点生成。

当前设计：

```text
dm_turn
  -> 生成 reply 文本
  -> evaluate_advancement
  -> enter_beat
  -> 生成 beat 过场文本
```

目标设计：

```text
dm_turn
  -> 只做裁定 / 规则前置 / 写入叙述素材
  -> evaluate_advancement
  -> 如果推进，则 enter_beat 构建新 scene
  -> final_narrate_turn 统一生成本回合唯一玩家可见叙述
```

`final_narrate_turn` 读取本回合所有结果：

- `user_input`
- `reply_brief`
- `last_check`
- `last_combat`
- `previous_scene`
- 当前 `scene`
- `story_transition`
- 最近 `messages`

然后只 append 一条：

```python
{"role": "dm", "content": text}
```

并只写一条：

```python
{"event": "narration", "text": text}
```

## 推荐主图

```text
START
  -> dm_turn
  -> route_session
      wait   -> evaluate_advancement
      combat -> run_combat -> narrate_aftermath? -> evaluate_advancement
  -> route_advancement
      stay    -> final_narrate_turn
      advance -> enter_beat -> final_narrate_turn
  -> route_ending
      ongoing -> END
      ending  -> epilogue
```

第一版建议进一步收敛：

```text
START
  -> dm_turn
  -> route_session
      wait   -> evaluate_advancement
      combat -> run_combat -> evaluate_advancement
  -> route_advancement
      stay    -> final_narrate_turn
      advance -> enter_beat -> final_narrate_turn
  -> route_ending
      ongoing -> END
      ending  -> epilogue
```

也就是第一版先移除独立的 `narrate_beat`，并考虑把 `narrate_aftermath` 也并入最终叙述，避免“战后叙述 + 切拍叙述”重复。

## 节点职责调整

### `dm_turn`

保留：

- `perceive`
- `dm_decide`
- `await_roll`
- `resolve_check`

调整：

- `narrate_reply` 不再生成玩家可见正文。
- `narrate_result` 不再生成玩家可见正文。

普通 reply 分支只产出：

```python
{
    "intent": "reply",
    "reply_brief": "...",
    "world_writes": writes,
    "next": "wait",
}
```

检定分支只产出：

```python
{
    "last_check": {...},
    "next": "wait",
}
```

如果保留函数名，可以把 `narrate_reply` 改名为 `prepare_reply`，把 `narrate_result` 改名为 `prepare_check_result`。若为了减少改动，也可以先保留节点名，但函数内容不 append `messages`。

### `evaluate_advancement`

职责不变：

- 消费 `world_writes`
- 判断全局胜负条件
- 判断当前拍推进条件
- 写入 `next_story`
- 命中推进时写入 `story.pending_next_beat_id`

建议增强：

命中推进时额外写入 `story_transition`：

```python
{
    "type": "advance",
    "from_beat_id": current_beat_id,
    "to_beat_id": target_beat_id,
    "reason": "命中的 trigger 描述或 id",
}
```

未推进时：

```python
{
    "type": "stay",
}
```

### `enter_beat`

职责仍是构建新场景，但需要保存切换前上下文：

```python
previous_scene = state.get("scene")
previous_story = state.get("story")
```

返回：

```python
{
    "previous_scene": previous_scene,
    "scene": scene,
    "story": story,
    "story_transition": {
        **existing_transition,
        "to_beat_title": beat.title,
        "to_location": scene.get("location"),
    },
    "campaign_log": log_event(..., {"event": "enter_beat", ...}),
}
```

`previous_scene` 是给最终叙述用的临时工作区，不是长期世界真相。

### `final_narrate_turn`

新增节点，放在 `src/session/story_nodes.py` 或单独 `src/session/narration_nodes.py`。

职责：

- 汇总本回合发生了什么。
- 调用 `world_bridge.narrate_turn_final(...)`。
- append 唯一 DM 消息。
- 写入唯一 narration 日志。
- 清理临时叙述工作区。

伪代码：

```python
async def final_narrate_turn(state: DMState) -> dict:
    text = await world_bridge.narrate_turn_final(
        user_input=state.get("user_input"),
        reply_brief=state.get("reply_brief"),
        last_check=state.get("last_check"),
        last_combat=state.get("last_combat"),
        previous_scene=state.get("previous_scene"),
        scene=state.get("scene") or {},
        story_transition=state.get("story_transition"),
        messages=state.get("messages"),
        use_llm=llm_enabled(state),
    )
    messages = list(state.get("messages", []))
    messages.append({"role": "dm", "content": text})
    return {
        "messages": messages,
        "campaign_log": log_event(state, {"event": "narration", "text": text}),
        "previous_scene": None,
        "story_transition": None,
    }
```

### `world_bridge.narrate_turn_final`

新增 DM 叙述函数。

输入：

```python
async def narrate_turn_final(
    *,
    user_input: str | None,
    reply_brief: str | None,
    last_check: dict | None,
    last_combat: dict | None,
    previous_scene: dict | None,
    scene: dict,
    story_transition: dict | None,
    messages: list[dict] | None,
    use_llm: bool,
    node_name: str = "dm",
) -> str:
```

prompt 规则：

- 如果 `story_transition.type == "advance"`：
  - 先承接玩家动作或结算结果。
  - 再自然描述场景切换。
  - 最后描述新场景可见要素和可行动方向。
- 如果没有推进：
  - 基于 `reply_brief` / `last_check` / `last_combat` 描述当前场景内的结果。
  - 保持玩家仍处于当前场景。
- 最后一句必须以“你可以”开头，给 2-3 个后续方向。
- 只输出玩家可见叙述，不输出 JSON。

## 状态字段新增

在 `DMState` 增加：

```python
previous_scene: dict | None  # 本回合切拍前的场景，仅供最终叙述承接
story_transition: dict | None  # 本回合故事推进摘要，仅供最终叙述使用
```

保留已有：

```python
reply_brief: str
say: str
```

`say` 暂时继续作为响应快捷字段，由 `_last_dm_say()` 计算，不作为状态真相源。

## `campaign_log` 约定

本方案下，一次玩家输入可以有多个结构事件：

- `ability_check`
- `combat`
- `advance`
- `enter_beat`
- `flag_set`
- `clue_delivered`

但应该只有一条玩家可见叙述事件：

```python
{"event": "narration", "text": "..."}
```

这能保证：

- `campaign_log` 仍保留完整结构化审计。
- 前端聊天流只看 `state.messages`。
- 调试时不会把结构事件误认为 DM 多次回复。

## WebSocket 行为

`final_narrate_turn` 调用 `dm_narrate()`，所以仍会发：

```json
{"type":"node_start","node":"dm"}
{"type":"stream","node":"dm","content":"..."}
{"type":"node_end","node":"dm"}
```

最终 HTTP payload 和 `session_update` 仍返回同一份最终状态。前端无需协议变更。

## 推荐实施顺序

1. 新增 `DMState.previous_scene` 和 `DMState.story_transition`。
2. 新增 `world_bridge.narrate_turn_final()`。
3. 新增 `story_nodes.final_narrate_turn()`。
4. 修改 `graph.py`，让所有非中断、非战斗终点进入 `final_narrate_turn`。
5. 修改 `dm_subgraph.narrate_reply()`，停止生成玩家可见消息。
6. 修改 `dm_subgraph.narrate_result()`，停止生成玩家可见消息。
7. 停用 `narrate_beat` 路由。
8. 编译验证和一次真实模型手测。

## 验证标准

对一次触发切拍的玩家输入，最终 payload 应满足：

```python
dm_messages = [m for m in state["messages"] if m["role"] == "dm"]
narrations = [e for e in state["campaign_log"] if e["event"] == "narration"]

payload["say"] == dm_messages[-1]["content"]
payload["say"] == narrations[-1]["text"]
```

并且本次玩家输入只新增一条 DM message。

对不触发切拍的普通输入：

- 只新增一条 DM message。
- 文本承接当前 scene。
- 不出现新拍标题。

对触发切拍的输入：

- 只新增一条 DM message。
- 文本先承接玩家动作，再自然进入新场景。
- `scene` 已经是新场景。
- `say` 描述的是新场景下可继续行动的状态。

## 风险

1. `final_narrate_turn` prompt 会更复杂，因为它需要同时处理普通 reply、检定、战斗、切拍。
2. 如果 `dm_turn` 不再提前生成正文，前端要等到推进判定完成后才开始看到流式文本；但这能换来一致性。
3. 若 `evaluate_advancement` 的 semantic trigger 本身调用 LLM，用户可见流式开始时间会晚于当前方案。

## 结论

不建议 `enter_beat` 后重新进入完整 `dm_turn` 子图。正确的复用边界是复用 DM 的叙述能力，而不是复用包含裁定和中断的完整 DM 回合。

推荐采用“最终统一叙述节点”：

- 中间节点只产出事实、规则结果和叙述素材。
- `final_narrate_turn` 统一生成唯一玩家可见回复。
- `say`、`messages`、`campaign_log` 自然保持一致。
